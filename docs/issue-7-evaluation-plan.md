# Issue #7: 現実に即した分析計画評価への改善計画

## この文書の位置付け

この文書は、Issue #7に対する現行実装の判断記録と、今後検証すべき案をまとめる。

- 「現行実装」と明記した項目は、現在のブランチ`issue-7-hoshino`に実装されている。
- チェック済みの実装タスクは現在のブランチで対応済み、チェックされていない項目、重大問題、新しい評価軸などは将来案であり、現在の動作ではない。
- 現行実装は、LLMによる意味評価を必須のまま維持し、Issue #7の「低品質な1タスクが他の高得点で相殺される問題」に変更範囲を限定する。
- 本文中の閾値は、固定評価セットによる校正が終わるまでは暫定値である。

## 現行実装の要約

現行実装の合格条件は次のとおりである。

1. OllamaまたはOpenRouterのLLMが既存の5軸を採点する。
2. 総合点が80点以上である。
3. 全タスクの`granularity`（分割粒度）が12点以上である。
4. 全タスクの`context`（コンテキスト充足）が12点以上である。
5. 2〜4をサーバー側で判定し、1件でも満たさなければ不合格にする。

したがって、総合点が80点以上でも、1タスクの分割粒度またはコンテキスト充足が11点以下なら不合格になる。LLMが直接合否を決めるのではなく、LLMは意味に基づく採点を担当し、プロダクトの合格条件はサーバーが決定的に適用する。

今回変更していないものは次のとおりである。

- LLM呼び出しを必須とする評価経路
- OllamaとOpenRouterのプロバイダー構成
- 既存の5評価軸と各20点、計100点の配点
- 初期案と完全一致する場合に画面側で採点を拒否する処理
- 総合点80点という既存の合格境界

重大問題による強制失格、新評価軸、禁止語判定、LLMを呼ばない事前採点、初期案との意味的な差分評価は、今回の実装には含めない。

## 背景

脆弱性調査シナリオでは、初期状態の文章がすでに具体的で安全な計画になっている。そのため、文章品質を素直に評価するLLMは未編集の初期案にも高得点を付ける。また、画面側の「初期案と完全一致なら採点しない」という判定は、1文字だけ変更すれば回避できる。

実装前の合否は総合点80点以上だけで決まり、タスク別の最低点や重大な問題による失格条件がなかった。分割粒度とコンテキスト充足も全タスクの平均だったため、一部の低品質なタスクを他の良いタスクが相殺できた。

このIssueでは、文章の長さや専門用語ではなく、入力証拠に基づいて安全かつ検証可能な作業をAIへ委任できるかを評価する仕組みに変更する。

## 実装前の確認結果

- 作業ブランチ: `issue-7-hoshino`
- `npm test`: 成功
- `npm run lint`: 成功
- 本番ビルドとトップページのHTTP応答: 成功
- Ollamaは現在の確認環境に未導入のため、実モデルによる点数比較は未実施
- 通常演習では初期案との完全一致だけを画面側で拒否する
- 評価APIはタスクのタイトル、指示、コンテキストの空文字を許容する
- 合否は総合点80点以上だけで判定する
- 無意味なタスクを他のタスクで相殺しないルールはLLMへの指示だけで、サーバー側では強制しない

上記は変更前の状態である。現行実装では、総合点に加えて全タスクの分割粒度とコンテキスト充足へ12点の最低点を設け、サーバー側で強制する。

## 現行実装の判断と根拠

### 1. LLMによる意味評価を必須のまま維持する

危険性や具体性は単語の有無だけでは判定できない。「DoSを実行する」と「DoSを実行しない」では意味が反対であり、単純な禁止語判定では後者を誤検出する。そのため、文章の意味を評価する処理は、従来どおり設定済みのOllamaまたはOpenRouterへ必ず依頼する。

根拠があること:

- 評価処理はプロバイダーのLLMを呼び出してから、応答を正規化している。
- LLMを呼ばず、ローカルルールだけで採点を完了する経路は追加していない。
- 否定や禁止を含む日本語を、危険語の出現だけで減点しないよう評価プロンプトに明記している。

まだ根拠がないこと:

- LLMが否定、禁止、条件を常に正しく解釈すること。
- OllamaとOpenRouter、またはモデルの違いにかかわらず同じ評価になること。

これらは、否定表現と危険な実行指示を対にした固定評価セットを複数回採点し、誤検出率と合否反転率を測定して確認する。

### 2. 既存の5評価軸と総合80点を維持する

Issue #7の直接原因は、総合点だけで合否を決め、タスクごとの弱点を平均で相殺できたことである。評価軸や総合点の境界まで同時に変えると、既存シナリオ全体へ影響し、どの変更が結果へ作用したか判断しにくくなる。そのため、既存の5軸と総合80点は維持し、タスク最低点だけを追加する。

この判断には変更範囲と回帰リスクを抑える根拠がある。一方、5軸および総合80点そのものが最適であるという実証的な根拠は今回取得していない。固定評価セットで誤合格率と誤不合格率を測定し、必要なら別Issueとして配点を校正する。

### 3. タスク別の点数アンカーを明示する

LLMへ、`granularity`と`context`を次の点数帯で評価するよう指示する。

- 0〜5点: 空欄、無意味な文字列、プレースホルダー、解釈不能
- 6〜9点: 「安全に確認する」などの一般論だけ
- 10〜11点: 対象と作業は分かるが、重要な要素が複数不足
- 12〜16点: おおむね実行可能だが、一部に不足または曖昧さがある
- 17〜20点: 対象、操作、入力・証跡、制約、出力、完了条件が明確

また、文章量、専門用語、丁寧な表現だけでは加点しない。`instruction`が無意味ならそのタスクの`granularity`を5点以下、`context`が無意味ならそのタスクの`context`を5点以下にする。他の良いタスクを理由に、低品質なタスク自身の点数を引き上げない。

抽象的な評価基準だけの場合より、点数と品質状態の対応を明示する方が採点理由を説明しやすいという設計上の根拠はある。ただし、実際のLLMがアンカーを安定して守ることはまだ実証していない。現在の自動テストはLLM応答後の合否計算を検証するものであり、「aaaaa」に実モデルが5点以下を返すことまでは証明しない。

### 4. 全タスクの分割粒度とコンテキスト充足に最低12点を要求する

平均点だけでは、例えば20点のタスクと11点のタスクが平均16点となり、後者の不足を隠せる。この相殺は平均値の性質によるため、平均の重みを調整するだけでは保証できない。全タスクへ最低点を設けることで直接防止する。

12点は、点数アンカー上で「重要な要素が複数不足する状態」と「おおむね実行可能な状態」の境界として選んだ。これは説明可能な初期値ではあるが、最適値であるという統計的根拠はない。10、11、12、13、15点などの候補を固定評価セットへ適用し、誤合格を優先して減らしつつ、許容できる誤不合格率になる境界を選ぶ必要がある。

### 5. 合否はサーバー側で計算する

LLMの出力には点数とフィードバックを求めるが、合否そのものは求めない。サーバーが総合80点と各タスク12点の条件から`passed`と`gateFailures`を生成する。

この方法では、同じ点数ならプロバイダーや実行回によらず同じ合否になる。また、「総合92点だがタスク2が11点なので不合格」のような理由を機械的に説明できる。LLMの採点が正しいことは別途検証が必要だが、採点後の合否規則が一貫して適用されることは自動テストで確認できる。

### 6. UIはサーバーの合否と不合格理由を使用する

画面側で総合点だけから合否を再計算せず、サーバーの`passed`を使用する。最低点により不合格になった場合は`gateFailures`を改善点より先に表示し、総合点が80点以上でも合格用の緑色表示にしない。

これはサーバーと画面の判定不一致を防ぐためであり、採点精度そのものを変える処理ではない。画面に表示する指摘は最大3件なので、多数のタスクが未達の場合は全理由を同時表示しないという制約が残る。

### 7. 自動テストが証明する範囲を限定する

現行テストでは次を確認する。

- 総合92点でも、1タスクの分割粒度とコンテキスト充足が11点なら不合格になる。
- 総合80点で、対象タスクの分割粒度とコンテキスト充足が16点なら合格になる。
- 不合格の場合、該当タスクと評価軸を示す理由が返る。

これは、LLMが返した点数に対するサーバーの計算を証明する。一方、実モデルが入力文章をどの点数にするか、同じ入力で点数が安定するかは証明しない。

## 根拠の強さ

### コードと自動テストで確認できるもの

- 評価時にLLMを呼び出すこと。
- 総合点が80点未満なら不合格になること。
- 1タスクでも分割粒度またはコンテキスト充足が12点未満なら不合格になること。
- 高得点タスクが低得点タスクの最低点違反を相殺できないこと。
- サーバーが合否と不合格理由を生成し、UIがその合否を使用すること。
- 現在の自動テスト、Lint、ビルドが成功すること。

### 問題構造から妥当と判断できるが、実モデルでは未検証のもの

- 点数アンカーの明示が、曖昧な採点を減らすこと。
- 無意味な文章への上限指定が、「aaaaa」への過大評価を減らすこと。
- 文章量や専門用語だけでは加点しない指示が、キーワードの水増しを抑制すること。
- 12点が「最低限実行可能」の境界として機能すること。

### 現時点で示せないもの

- 12点が最適な閾値であること。
- 実モデルが無意味または具体性の低い文章を毎回12点未満にすること。
- OllamaとOpenRouter、異なるモデル間で同程度の結果になること。
- 同じモデルで繰り返したときに合否が反転しないこと。
- 初期案へ1文字だけ追加した提出を必ず不合格にできること。
- 危険な内容を総合点にかかわらず必ず不合格にできること。

OpenRouterの多くのモデルでHTTP 429が発生しているため、現時点では実モデルによる反復評価を後回しにしている。

## 現行実装で解決しない問題

### 成果物の品質と学習行動は別の評価対象である

Issue #7には、「無意味または低品質な文章が合格する問題」と「学習者が実質的に編集しなくても合格する問題」が含まれる。

現行実装は前者を対象とする。完全無変更は既存の文字列比較で拒否するが、初期案がすでに高品質なら、末尾へ1文字追加した文章も品質自体はほぼ同じである。品質評価を正しく行ったLLMがこれを高得点にしても、必ずしも採点ミスとはいえない。

後者を解決するには、最終文章の品質とは別に、初期案から意味のある改善を行ったかを評価する必要がある。初期案と提出案の意味的差分を評価する、変更理由を入力させる、または初期案を未完成な下書きにするなどの設計が必要であり、今回の変更には含めない。

### 危険な内容の強制失格は未実装である

現行ゲートは分割粒度とコンテキスト充足だけをタスク最低点として扱う。理論上、安全性が0点でも他の4軸が20点なら総合80点となり、タスク最低点も満たせば合格できる。

「危険な内容は総合点にかかわらず不合格」という要件を採用する場合は、安全性の最低点または根拠箇所付きの`criticalIssues`を別途実装する必要がある。これはIssue #7の今回の変更範囲を超えるため実装していない。

## 未検証事項の確認方法

少なくとも次の固定入力へ、人手で期待する点数範囲と合否を事前に付ける。

- 初期文章の完全無変更
- 初期文章への1文字追加
- 1タスクの`instruction`が`aaaaa`
- 1タスクの`context`が`aaaaa`
- 「安全に確認して報告する」だけの一般的な指示
- 長文だが具体的な操作、証跡、成果物がない指示
- 「DoSは行わない」という禁止指示
- 「DoSを実行する」という危険な実行指示
- 対象、操作、入力・証跡、制約、出力、完了条件が明確な合格例

各入力を対象モデルで5〜10回ずつ評価し、次を記録する。

- 誤合格率: 人手では不合格だがモデルとゲートが合格にした割合
- 誤不合格率: 人手では合格だが不合格にした割合
- 合否反転率: 同じ入力の反復評価で合否が変わった割合
- 評価軸別、タスク別の平均点と分散
- 人手判定とモデル判定の一致率

閾値は、10、11、12、13、15点などを同じ結果へ適用して混同行列を比較する。Issue #7では誤合格を減らすことを優先するが、許容する誤不合格率は別途合意する。実モデルの校正が終わるまでは、現在の12点を暫定値として扱う。

## 目標

次の状態を合格とする。

> 学習者が、各タスクの対象・入力証拠・操作・制約・成果物・完了条件を具体化し、情報が不足した場合に推測で補わず停止または保留できる分析計画を作れている。

優先するのは、実際には不十分な計画を合格させる「誤合格」を減らすことである。採点は教育上の支援であり、実環境の安全性や分析結果の正しさを保証するものにはしない。

## 用語と判定単位

ハルシネーションは、入力資料から確認できない内容を、確認済みの事実として出力することと定義する。

実行結果を将来評価する場合、主張を次の単位に分類する。

- `supported`: 入力証拠から確認できる
- `contradicted`: 入力証拠と矛盾する
- `unsupported`: 入力に根拠がない
- `inference`: 根拠付きの推測として明示されている
- `unknown`: 判断不能として適切に保留されている

このIssueの第1段階では、実際の分析を実行せず、上記の区別を行いやすいプロンプトになっているかを静的に評価する。

## 評価設計

### 評価軸

100点満点を維持し、次の5軸を各20点で評価する。

1. タスク分解・実行可能性
   - 1タスクが1つの判断単位になっている
   - 対象と具体的な操作が分かる
   - 前後のタスクとの受け渡しが分かる
2. 証拠グラウンディング
   - 使用できる入力、ログ、設定、前段成果物が特定されている
   - 結論をどの証拠に結び付けるかが分かる
   - 入力にない事実を補完しない
3. 不確実性・保留
   - 事実、推測、未確認事項を区別する
   - 情報不足時の停止、保留、確認依頼が定義されている
   - 結論を強制しない
4. 検証可能性・成果物
   - 出力形式と必須項目が具体的である
   - 完了条件、照合方法、反証条件がある
   - 第三者が根拠を追跡できる
5. 安全性・権限境界
   - 許可された対象と操作範囲が分かる
   - 機密情報、破壊的操作、外部接続などの扱いが明確である
   - 停止条件、承認、可逆性が考慮されている

文章量、専門用語の数、丁寧な表現そのものには加点しない。

### 点数アンカー

各評価軸は次のアンカーを共通で使う。

- 0点: 空欄、無意味な文字列、または指示として解釈できない
- 5点: 一般論だけで対象や成果物を特定できない
- 10点: 対象と作業は分かるが、入力、制約、成果物、完了条件の重要部分が不足する
- 15点: 実行に必要な情報がほぼ揃い、一部だけ不足する
- 20点: 入力、操作、制約、成果物、完了条件が明確で、そのまま安全に委任できる

中間点は、どの必須要素が満たされているかに基づいて付ける。単なる印象評価にしない。

### タスク単位の必須要素

各タスクについて、次を個別に判定する。

- `target`: 何を対象にするか
- `action`: 何を確認、比較、整理するか
- `evidence`: どの入力や前段成果物を使うか
- `constraints`: 何をしてはいけないか、どこで停止するか
- `artifact`: 何をどの形式で返すか
- `completion`: 何を満たせば完了か

タスク別評価を単純平均するだけでなく、最低品質を合否条件に含める。

### 合格条件

初期の基準は次とし、固定評価セットによる調整後に確定する。

- 総合点が80点以上
- 証拠グラウンディング、不確実性・保留、安全性・権限境界がそれぞれ16点以上
- 全タスクの最低点が12点以上
- 重大問題が0件
- 空欄、プレースホルダー、無意味な文字列を含むタスクがない

最終的な合否はLLMに直接決めさせず、正規化後の点数と重大問題からサーバー側で決定する。

## 重大問題

単語のブラックリストではなく、文章中の意味と肯定・否定を評価する。「DoSを実行する」と「DoSを実行しない」を同じ判定にしてはいけない。

次の意味を持つ指示は重大問題として扱う。

- `fabrication_required`: 不足情報、値、証拠、引用を推測または捏造して補う
- `uncertainty_suppressed`: 不明や未確認と回答することを禁止する
- `conclusion_forced`: 証拠にかかわらず特定の結論を要求する
- `evidence_ignored`: 反証や矛盾する証拠を無視させる
- `source_fabricated`: 未確認の資料や架空の出典を参照済みとして扱う
- `unauthorized_action`: 許可されていない対象や実環境への操作を要求する
- `destructive_action`: 破壊的変更、DoS、証拠の上書きなどを実行させる
- `secret_exposure`: 資格情報や機密情報の外部送信、復元、不要な記録を要求する
- `embedded_instruction_following`: ログや検体に含まれる命令文をデータではなく指示として実行させる
- `non_actionable_task`: 空欄、無意味な文字列、または一般論だけで実行不能である

LLMが重大問題を返す場合は、入力中の根拠箇所を短い引用として必須にする。サーバー側で、その引用が実際の入力に存在することを検証する。

### 単独では減点しない用語

次の用語は曖昧になりやすいが、使用しただけでは減点しない。

- 適切に
- 安全に
- 詳しく
- 必要に応じて
- 十分に
- 完全に
- 総合的に判断する
- ベストプラクティスに従う

これらの後に具体的な対象、操作、制約、完了条件がなければ減点する。

## 現行の評価順序

LLM呼び出しを必須とするため、現行実装では次の順序で評価する。

1. OllamaまたはOpenRouterのLLMによる意味評価
   - 既存5軸と全タスクの分割粒度、コンテキスト充足を構造化出力させる
2. 応答の正規化
   - 必須評価軸、点数範囲、タスク別結果を検証する
3. サーバー側の合否計算
   - 総合80点と全タスク12点の条件を機械的に適用する
4. UIへの結果表示
   - 合否、最低点を満たさないタスク、LLMの改善点を表示する

空欄やプレースホルダーをLLM呼び出し前に不合格とする事前採点は、LLM必須の方針と異なるため今回実装しない。危険な意味の判定も、単純な正規表現や禁止語だけでは行わない。

## 将来の実行評価

静的なプロンプト評価だけでは、実際のハルシネーション発生率は保証できない。将来、分析結果を生成する機能を追加する場合は、次の固定ケースを使った実行評価を別機能として設計する。

1. 必要な証拠がすべてある
2. 結論に必要な証拠が欠けている
3. 証拠同士が矛盾している
4. 無関係なログが混在している
5. ログや検体内に命令文が含まれている
6. 異常が存在しない正常ケース

測定候補は次のとおり。

- 根拠付き主張率
- 未根拠断定率
- 証拠カバレッジ
- 回答不能ケースの適切な保留率
- 回答可能ケースの過剰保留率
- 複数回実行時の重要事実・結論の不一致率
- 無許可または危険な操作の提案率

実行評価は実際の検体実行や攻撃を意味しない。架空の固定入力と期待結果を使う。

## 将来計画まで含めた完了条件

以下は現行の最小実装だけでなく、上記の将来案と実モデル校正まで含めた完了条件である。現時点では未達の項目を含む。

- 固定評価セットについて、人手で不合格とした重大問題例の誤合格が0件である
- `aaaaa`、空欄、一般論だけのタスクを含む計画は合格できない
- 1文字だけの変更では初期案を合格状態にできない
- 1件の低品質タスクを他のタスクの高得点で相殺できない
- 「DoSを行わない」などの禁止表現を危険指示として誤検出しない
- 具体的な入力、証拠、制約、成果物、完了条件、保留条件を持つ計画は合格できる
- 合否の根拠をタスク単位で画面から確認できる
- 自動テスト、Lint、ビルドが成功する
- 対応モデルと校正結果が文書化されている

## 対象外

- 実在するシステムへの脆弱性診断
- 検体、攻撃コード、能動的スキャンの実行
- LLM評価を実環境の安全性保証として利用すること
- あらゆるモデルで同じ点数を保証すること
- 単語ブラックリストだけによる危険性判定
