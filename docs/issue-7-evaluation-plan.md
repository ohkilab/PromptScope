# Issue #7: 現実に即した分析計画評価への改善計画

## 背景

脆弱性調査シナリオでは、初期状態の文章がすでに具体的で安全な計画になっている。そのため、文章品質を素直に評価するLLMは未編集の初期案にも高得点を付ける。また、画面側の「初期案と完全一致なら採点しない」という判定は、1文字だけ変更すれば回避できる。

現在の合否は総合点80点以上だけで決まり、タスク別の最低点や重大な問題による失格条件がない。分割粒度とコンテキスト充足も全タスクの平均なので、一部の低品質なタスクを他の良いタスクが相殺できる。

このIssueでは、文章の長さや専門用語ではなく、入力証拠に基づいて安全かつ検証可能な作業をAIへ委任できるかを評価する仕組みに変更する。

## 現状の確認結果

- 作業ブランチ: `issue-7-hoshino`
- `npm test`: 成功
- `npm run lint`: 成功
- 本番ビルドとトップページのHTTP応答: 成功
- Ollamaは現在の確認環境に未導入のため、実モデルによる点数比較は未実施
- 通常演習では初期案との完全一致だけを画面側で拒否する
- 評価APIはタスクのタイトル、指示、コンテキストの空文字を許容する
- 合否は総合点80点以上だけで判定する
- 無意味なタスクを他のタスクで相殺しないルールはLLMへの指示だけで、サーバー側では強制しない

## 目標

次の状態を合格とする。

> 学習者が、各タスクの対象・入力証拠・操作・制約・成果物・完了条件を具体化し、情報が不足した場合に推測で補わず停止または保留できる分析計画を作れている。

優先するのは、実際には不十分な計画を合格させる「誤合格」を減らすことである。採点は教育上の支援であり、実環境の安全性や分析結果の正しさを保証するものにはしない。

## 用語と判定単位

ハルシネーションは、入力資料から確認できない内容を、確認済みの事実として出力することと定義する。

実行結果を将来評価する場合、主張を次の単位に分類する。

- `supported`: 入力証拠から確認できる
- `contradicted`: 入力証拠と矛盾する
- `unsupported`: 入力に根拠がない
- `inference`: 根拠付きの推測として明示されている
- `unknown`: 判断不能として適切に保留されている

このIssueの第1段階では、実際の分析を実行せず、上記の区別を行いやすいプロンプトになっているかを静的に評価する。

## 評価設計

### 評価軸

100点満点を維持し、次の5軸を各20点で評価する。

1. タスク分解・実行可能性
   - 1タスクが1つの判断単位になっている
   - 対象と具体的な操作が分かる
   - 前後のタスクとの受け渡しが分かる
2. 証拠グラウンディング
   - 使用できる入力、ログ、設定、前段成果物が特定されている
   - 結論をどの証拠に結び付けるかが分かる
   - 入力にない事実を補完しない
3. 不確実性・保留
   - 事実、推測、未確認事項を区別する
   - 情報不足時の停止、保留、確認依頼が定義されている
   - 結論を強制しない
4. 検証可能性・成果物
   - 出力形式と必須項目が具体的である
   - 完了条件、照合方法、反証条件がある
   - 第三者が根拠を追跡できる
5. 安全性・権限境界
   - 許可された対象と操作範囲が分かる
   - 機密情報、破壊的操作、外部接続などの扱いが明確である
   - 停止条件、承認、可逆性が考慮されている

文章量、専門用語の数、丁寧な表現そのものには加点しない。

### 点数アンカー

各評価軸は次のアンカーを共通で使う。

- 0点: 空欄、無意味な文字列、または指示として解釈できない
- 5点: 一般論だけで対象や成果物を特定できない
- 10点: 対象と作業は分かるが、入力、制約、成果物、完了条件の重要部分が不足する
- 15点: 実行に必要な情報がほぼ揃い、一部だけ不足する
- 20点: 入力、操作、制約、成果物、完了条件が明確で、そのまま安全に委任できる

中間点は、どの必須要素が満たされているかに基づいて付ける。単なる印象評価にしない。

### タスク単位の必須要素

各タスクについて、次を個別に判定する。

- `target`: 何を対象にするか
- `action`: 何を確認、比較、整理するか
- `evidence`: どの入力や前段成果物を使うか
- `constraints`: 何をしてはいけないか、どこで停止するか
- `artifact`: 何をどの形式で返すか
- `completion`: 何を満たせば完了か

タスク別評価を単純平均するだけでなく、最低品質を合否条件に含める。

### 合格条件

初期の基準は次とし、固定評価セットによる調整後に確定する。

- 総合点が80点以上
- 証拠グラウンディング、不確実性・保留、安全性・権限境界がそれぞれ16点以上
- 全タスクの最低点が12点以上
- 重大問題が0件
- 空欄、プレースホルダー、無意味な文字列を含むタスクがない

最終的な合否はLLMに直接決めさせず、正規化後の点数と重大問題からサーバー側で決定する。

## 重大問題

単語のブラックリストではなく、文章中の意味と肯定・否定を評価する。「DoSを実行する」と「DoSを実行しない」を同じ判定にしてはいけない。

次の意味を持つ指示は重大問題として扱う。

- `fabrication_required`: 不足情報、値、証拠、引用を推測または捏造して補う
- `uncertainty_suppressed`: 不明や未確認と回答することを禁止する
- `conclusion_forced`: 証拠にかかわらず特定の結論を要求する
- `evidence_ignored`: 反証や矛盾する証拠を無視させる
- `source_fabricated`: 未確認の資料や架空の出典を参照済みとして扱う
- `unauthorized_action`: 許可されていない対象や実環境への操作を要求する
- `destructive_action`: 破壊的変更、DoS、証拠の上書きなどを実行させる
- `secret_exposure`: 資格情報や機密情報の外部送信、復元、不要な記録を要求する
- `embedded_instruction_following`: ログや検体に含まれる命令文をデータではなく指示として実行させる
- `non_actionable_task`: 空欄、無意味な文字列、または一般論だけで実行不能である

LLMが重大問題を返す場合は、入力中の根拠箇所を短い引用として必須にする。サーバー側で、その引用が実際の入力に存在することを検証する。

### 単独では減点しない用語

次の用語は曖昧になりやすいが、使用しただけでは減点しない。

- 適切に
- 安全に
- 詳しく
- 必要に応じて
- 十分に
- 完全に
- 総合的に判断する
- ベストプラクティスに従う

これらの後に具体的な対象、操作、制約、完了条件がなければ減点する。

## 効率化方針

評価は次の順で行い、明白な不合格に高価なLLM判定を使わない。

1. 決定的な事前検査
   - 空欄、プレースホルダー、文字列反復、件数、長さ、重複IDを確認する
2. LLMによる意味評価
   - 評価軸、タスク別不足、重大問題、根拠箇所を構造化出力させる
3. サーバー側の合否計算
   - 点数の下限と重大問題から機械的に決定する
4. 境界事例の再評価
   - 閾値付近だけ複数回評価し、結果が安定しない場合は合格にしない

危険な意味の判定を単純な正規表現だけで行わない。一方、空欄や明白なプレースホルダーのように決定的に判定できるものはLLMへ送る前に処理する。

## 将来の実行評価

静的なプロンプト評価だけでは、実際のハルシネーション発生率は保証できない。将来、分析結果を生成する機能を追加する場合は、次の固定ケースを使った実行評価を別機能として設計する。

1. 必要な証拠がすべてある
2. 結論に必要な証拠が欠けている
3. 証拠同士が矛盾している
4. 無関係なログが混在している
5. ログや検体内に命令文が含まれている
6. 異常が存在しない正常ケース

測定候補は次のとおり。

- 根拠付き主張率
- 未根拠断定率
- 証拠カバレッジ
- 回答不能ケースの適切な保留率
- 回答可能ケースの過剰保留率
- 複数回実行時の重要事実・結論の不一致率
- 無許可または危険な操作の提案率

実行評価は実際の検体実行や攻撃を意味しない。架空の固定入力と期待結果を使う。

## 完了条件

- 固定評価セットについて、人手で不合格とした重大問題例の誤合格が0件である
- `aaaaa`、空欄、一般論だけのタスクを含む計画は合格できない
- 1文字だけの変更では初期案を合格状態にできない
- 1件の低品質タスクを他のタスクの高得点で相殺できない
- 「DoSを行わない」などの禁止表現を危険指示として誤検出しない
- 具体的な入力、証拠、制約、成果物、完了条件、保留条件を持つ計画は合格できる
- 合否の根拠をタスク単位で画面から確認できる
- 自動テスト、Lint、ビルドが成功する
- 対応モデルと校正結果が文書化されている

## 対象外

- 実在するシステムへの脆弱性診断
- 検体、攻撃コード、能動的スキャンの実行
- LLM評価を実環境の安全性保証として利用すること
- あらゆるモデルで同じ点数を保証すること
- 単語ブラックリストだけによる危険性判定
